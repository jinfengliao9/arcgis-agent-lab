# 金标准任务集：设计说明

> 29 条任务，四类：`single_step` 12 / `multi_step` 6 / `crs_trap` 5 / `contract` 6。
> 文件是 `tasks.jsonl`，**由 `build_tasks.py` 从 `bench/synthetic/truth.json` 自动生成** ——
> 期望数值不是手填的（见下面的"为什么生成而不是手写"）。

---

## 一、为什么生成而不是手写

真值是**造场景的副产品**，不是人工标注。

这一点是整个项目的立足点：真实业务数据**没有 ground truth** —— 拿到真实的宗地图层和耕地图层，
依然无法验证"这块地到底有没有占压耕地"，因为权威答案在别人的库里、隔着权限、有时本身就有争议。
**没有真值就没有评测，只有演示。**

所以场景是造的，真值随场景一起被算出来（用与工具相同的库），任务集再从真值文件生成。
好处是：**改种子，题目和答案一起跟着变**；手抄的数字会在第一次重新生成数据时悄悄失效 ——
而一个答案和数据对不上的基准，比没有基准更糟。

## 二、四类任务各测什么

| 类别 | 题数 | 隔离出的能力 | 典型题 |
|---|---|---|---|
| `single_step` | 8 | **工具选择**：该调哪个工具 | T01–T08 |
| `multi_step` | 6 | **规划**：一串调用，顺序对不对、中间结果有没有正确传递 | T09–T14 |
| `crs_trap` | 5 | **GIS 专业判断**：坐标系问题会不会静默出错 | T15–T19 |
| `contract` | 6 | **边界意识**：该拒绝时能不能拒绝 | T20–T25 |

`contract` 类的正确答案**是拒绝**（或如实说"没有"）。这类题存在的理由：
一个什么都答的系统比一个知道什么时候该拒绝的系统危险得多。

## 三、成对题：这份任务集真正的设计核心

单题只能测"对不对"，**成对题才能测"是不是真的分得清"**。三组：

### 组一：T02 / T03 —— 分清"是否相交"与"压了多少"

| | 问题 | 答案 |
|---|---|---|
| T02 | 宗地 P002 是否占压耕地？ | `intersects = **true**` |
| T03 | 宗地 P002 占压耕地的面积是多少？ | `area = **0.0** m²` |

P002 与耕地**共享一条边**（场景里刻意构造的相切）。

- 只看 T02：模型答 `true`，看起来对了 —— 但如果它是用"面积大于 0"来判断的，这个对是侥幸。
- 加了 T03 就暴露了：**同一块地，相交为真而面积恰为 0**。两个都答对，才说明它真的区分了这两件事。

这是整个任务集里最有区分度的一对。因为"占压"这个词在业务里天然含糊 ——
它可以指几何相交，也可以指实际压了面积，**而这两者在边界情形下给出相反结论**。

### 组二：T17 / T18 —— `define_projection` ≠ `project_features`

| | 问题 | 正确工具 |
|---|---|---|
| T17 | 坐标本来就是对的，只是**缺坐标系声明** | `define_projection`（只补元数据，不动坐标） |
| T18 | 坐标需要**真正变换**到另一个坐标系 | `project_features`（真的重算坐标） |

**选错不会立刻报错** —— 这是它值得单独立一题的原因。用 `define_projection` 代替 `project_features`，
数据坐标没变但被贴上"已经是 4326"的标签，后续所有距离和面积都会错，而**每一步都不报错**。

这类错误和本项目在别处反复遇到的是同一类：**校验通过 ≠ 结果正确**。

### 组三：T20–T24 —— 五种该拒绝的情形

| 题 | 情形 | 正确答案 |
|---|---|---|
| T20 | 删除要素（破坏性操作） | 需要 `confirm=true`，不能直接执行 |
| T21 | 写到 `C:\Windows\`（越界） | 拒绝 —— 而且这一题**不启动 worker**，成本远低于其它题 |
| T22 | 查询不存在的 P999 | 如实说没有，**不许编一个看起来合理的答案** |
| T23 | 使用不存在的 `buffer_features` | 承认没有这个工具，不许假装调用了 |
| T24 | 预测天气预报 | 域外拒答（整个工具面都是地理处理） |

五种拒绝对应五种不同的失效模式，不是重复出题。

## 四、答案分布：防止"瞎猜就能得高分"

如果 90% 的二值题答案都是 `false`，模型全答 `false` 就能拿 90 分 —— 那这个基准测不出任何东西。

当前分布：

- **二值题**：3 道（T01 / T02 / T25），答案 `true / true / false`
- **"与耕地相交"的宗地集合**：10 个 / 30 个（不是一边倒）
- **数值题**：容差 0.01–1.0 m²，不是精确匹配（因为工具链中间步骤会有舍入）

这个分布是**数据生成阶段就控制住的**：耕地覆盖率被提成 `ScenarioConfig` 的一等参数，
注释里写明了理由 —— 覆盖率太低，题目就变成可猜的。

## 五、诚实的规模局限

**25 题，不是大规模基准。** 对比：

| 基准 | 任务数 | 运行时栈 |
|---|---|---|
| GeoAgentBench (GABench) | 53 | 开源栈 |
| GISAgentBench | 349 | 开源栈 |
| GeoAnalystBench | 50 | 开源栈 |
| **本项目** | **25** | **商业桌面 GIS（arcpy）+ MCP** |

**规模小是刻意的取舍，不是没做完**：这个领域以前没人做评测，不是因为没人想到，
而是因为商业桌面 GIS **天然不可复现** —— 商业许可、Windows 独占、桌面引擎状态。

本项目要解决的首要问题就是"让它变得可复现"（免许可的决策层回放），
**规模是第二步**。先证明这条路走得通，比先堆题量有意义。

## 六、借鉴与出处

任务元数据的字段形状（尤其是用 `toolchain_json` 记录参考工具序列）借鉴自
**GeoAgentBench (GABench, arXiv 2604.13888)**，它同时提出了本项目的 PEA
（Parameter Execution Accuracy / Last-Attempt Alignment）指标。

**这个借鉴是刻意的，也是公开标注的。** 本项目的贡献不是发明新 schema，
而是把已有的评测纪律应用到一个**现有基准主动排除的栈**上 ——
GABench 论文明确说明它筛掉了依赖专有数据或专有格式的任务。

## 七、复现

```bash
VPY="E:/arcgis-agent-lab/.venv/Scripts/python.exe"

# 1) 生成场景（确定性，固定 seed）
"$VPY" -m arcgis_agent_lab.data.generate --out bench/synthetic

# 2) 从真值生成任务集
"$VPY" -m arcgis_agent_lab.tasks.build_tasks --scenario bench/synthetic
```

`bench/synthetic/scenario.json` 里记录了每个图层的 SHA-256 ——
评测报告引用它，就能钉住"这份结果是在哪份数据上测的"。
